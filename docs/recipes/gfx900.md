# Native HIP on gfx900 (Vega 10)

`-Dhip-arch=gfx900` builds the HIP engine's kernels for Vega 10 (RX Vega 56 and 64: wave64, 56 or 64 CUs, 8 GiB HBM2). The
fp16 MLX affine families that run on RDNA2 take the same path here: the stream, row, lanes, K-parallel and block tiles with
`DotF16`, the decode and plan kernels, attention and the DeltaNet recurrence. gfx900 has no `v_dot2_f32_f16`, no dot4, no matrix
cores and no bf16, so the bf16 and WMMA tiles are not built for it and the registry never selects them.

Status: the kernels of all sixteen groups compile for gfx900 and the host tests pass. No kernel has run on a gfx900 GPU yet;
the card runs are listed under "Not yet verified". The RDNA code objects are unchanged (the table below says how that is checked).

## Build

```sh
zig build native-hip tf-qwen35-test -Dhipcc=<rocm>/bin/hipcc -Dhip-arch=gfx900 -Doptimize=ReleaseFast
```

`hipcc` is ROCm's, or anything that takes `hipcc --genco` with `--offload-arch=gfx900`, the HIP headers and the device
bitcode (`-Dhip-include`, `-Dhip-device-lib`). `-Dhip-arch` names one exact chip of `zig/src/hip/caps.zig`; the code objects are
built for the processor with xnack and sramecc left open, so the device's own `gfx900:xnack-` name matches (`device_arch.zig`
drops the feature modes from the name the runtime reports).

## Runtime

The engine loads the HIP runtime library (`libamdhip64.so`, or the file `TENSORFOLD_HIP` names) and refuses it unless the
symbols of `zig/src/hip/abi.zig` and `hipGetDevicePropertiesR0600` resolve. Nothing gfx900-specific is asked of it beyond a
device that reports `gfx900` in its properties. The wavefront width comes from the caps table (`wave = 64`); the runtime
tests compare it with the device's own `warpSize`.

## What differs from RDNA

The kernels are written in groups of 32 lanes: every shuffle takes width 32 and a "wave" in them is `threadIdx.x >> 5`. On
wave64 a group of 32 is half of a wavefront and a width-32 shuffle never leaves it, so the tiles keep their lane arithmetic,
their reduction trees and their bits. What changed is what saw the whole wavefront, or used an instruction gfx900 lacks:

| Change | Where | RDNA code |
| --- | --- | --- |
| `gfx900` row of the caps table: `wave = 64`, no dot2, dot4 or matrix, fp16 activations, generation `gcn5`; `-mno-wavefrontsize64` only for wave32 rows | `src/hip/caps.zig`, `build/hip.zig` | unchanged |
| `TF_FDOT2(x, q, acc)`: `__builtin_amdgcn_fdot2` where the instruction exists (a macro, so those objects keep their bytes); on gfx900 the two products (each exact in fp32) fused into the accumulator one after the other | `common/fdot2.hpp`; `attention_fa.hip`, `prefill.hpp`, `dot2.hip`, `DotF16` | same code |
| `DotF16::quad`: the `v_dot2c_f32_f16_dpp` asm stays RDNA2's; others move x across the quad, then `TF_FDOT2` | `common/dot2.hpp` | same code |
| `narrow_product` (silu(gate) * up rounded once to fp16): `v_fma_mixlo_f16` stays; gfx900 has only `v_mad_mixlo_f16`, so the exact product in double is narrowed to half in one rounding | `tiles/epilogue.hpp` | same code |
| `readfirstlane(tid >> 5)` held a group index in a scalar register, wrong when two groups share a wavefront: `group32(tid)` | `common/wave.hpp`, `tiles/gemm.hpp` | same code |
| top-k's `__ballot` compaction counted lanes `& 31` of a 64-bit mask: lane and wave from `TF_WAVE` | `ops/draw.hpp` (`tf_topk`) | same code |
| DPP `row_xmask`, `permlane16` and `permlanex16` (gfx10+) in the prefill attention and the plan kernel: width-16 and width-32 shuffles on gfx900 | `attention/prefill.hpp`, `decode/plan.hip` | same code |
| `kGen` and `kWave` for gfx900; a `static_assert` of the wave width against the architecture | `common/arch.hpp` | unchanged |
| a registry cost table (`src/hip/tuning/gfx900.zon`); `tableFor` and `chip()` name the generation `gcn5` | `launches/affine.zig`, `launches/mlx_entries.zig`, `native/hip.zig` | unchanged |
| the stream tile takes at most 4 columns a lane on gfx900, and at most 8 columns times rows over several rows | `launches/stream_pick.zig` | unchanged |

Warp-synchronous code that was lock-step on 32 lanes is lock-step on 64, and `__syncwarp()` is a wavefront barrier, so the
`gemm_kp` tile's LDS hand-offs between the two groups of a wavefront stay ordered. A block of 32 threads fills half a wavefront.

A dot2 sums its two products with one rounding (the instruction) or two (the fused pair), so the bits of an fp16 product on
gfx900 are the fused pair's, not necessarily RDNA's golden files'. Every tile on gfx900 uses the same pair, so the tiles agree
with each other (solo equals batched, resumed equals fresh).

### Register pressure

From the amdhsa metadata of the objects built for gfx900 (no timing): the stream tile instantiations with 8 columns a lane, or
4 columns over 4 rows, spill their registers (up to 575 VGPRs), and so does the 128-row GEMM tile (`affine_gemm_block`, 195 to
227 of 256). The selection never picks them on gfx900: `stream_pick.zig` stops at 4 columns a lane and at 8 columns times
rows, and `gfx900.zon` leaves out the 128-row `gemm` entries, so the reference block tile (`block`, 223 VGPRs, no spill)
takes every prompt and decode call that tile would take. All the tiles of a family give the same bits, so this changes speed
only. The K-parallel tiles `affine_gemm_kp` spill 15 to 82 VGPRs and stay in the table. The costs in `gfx900.zon` are
gfx1030's thresholds with those changes, not measurements on a Vega; a measured table replaces them (`hip-affine-tune`).

### Kernel contract

gfx900's limits are not in the records of `zig/src/core/contract/hip_records*.zig`, which pin what hipcc made of every launch
on gfx1030, gfx1100, gfx1151 and gfx1201. The RDNA2 family's launches (those the records serve on gfx1030) are checked on
gfx900 in `hip-kernel-contract-limits` from its code objects, with no recorded numbers: wave size 64, threads against the
launch bound, VGPRs a wave and a SIMD (256 each, one 64 KiB register file a SIMD) and LDS against the chip row in
`limits.zig`, and the two planted controls must go red on it too. A launch the records mark unserved on gfx1030 (the bf16
and WMMA tiles) is not checked on gfx900. On a card, `hip-kernel-contract -Dhip-arch=gfx900` checks the loaded kernels
against the device's own limits the same way.

## Offline verification

Everything below runs without a gfx900 GPU. `<rocm>` is a ROCm 7.x tree or a `hipcc --genco`-compatible wrapper over a clang
with the AMDGPU target.

| Check | What it shows |
| --- | --- |
| `zig build hip-host-test -Dhip=true -Dhip-arch=gfx900` (and `gfx1030`) | the HIP admission tests build and pass with either arch |
| `zig build hip-kernel-build -Dhip=true -Dhipcc=<rocm>/bin/hipcc -Dhip-arch=gfx900` | all sixteen kernel groups compile for gfx900 and their GPU tests build |
| the same with `-Dhip-arch=gfx1030` on this branch and on the base, `.text` of each `group*.hsaco` compared | RDNA2 objects are byte for byte the base's |

## Not yet verified

- Any kernel on a gfx900 GPU: `zig build hip-kernel-test`, `hip-affine-test`, `hip-gpu-test` and `tf-qwen35-test` with
  `-Dhip-arch=gfx900` on the card, and `hip-kernel-contract` there.
- Every number in `gfx900.zon` is gfx1030's or a spill-driven choice.
- The code objects of the bf16 and WMMA groups for gfx1100 to gfx1201 were not rebuilt on the machine that made this change
  (its clang takes the gfx11 builtins with other types than ROCm's), so the byte comparison covers gfx1030 only.

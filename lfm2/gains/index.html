Gain 2 · cheap windows · M4 Pro · #867 and #868

Cheaper windows.

A window is several rows in one step. The rows come from a draft check, or one row comes from each stream. Decode time is mostly weight reads. In #821 to #823, each extra row costs about half of a full step. #867 and #868 share the reads across the rows. One-row decode does not change. Every row keeps its bits.

01 · dense projections

One read for 4 rows

The twin reads each weight once for up to 4 rows, at 4, 6 and 8 bits. From 8 rows, it uses simdgroup MMA.

02 · experts

One read per expert

From 16 rows, the GPU groups the picks by expert. It reads each picked expert once for all of its rows.

03 · 6-bit head

Shared head reads

The tied embedding head shares its reads across the rows of a window.

Expert reads in one MoE layer, 16-row window

Each row picks 4 of 64 experts, so there are 64 picks. A lit cell has been read. After the change, all cells of one expert light up together. This is one read.

The picks are invented for this picture.

Gain 3 · tensor units · M5 Ultra · #871 and #873

Tensor units on the M5.

The M5 GPU has tensor units: hardware for small matrix products. mlx-lm uses them for prompts. The PR head (#821 to #868) does not use them. #871 and #873 move the LFM2 prompt path onto them on the M5 and later. The new path uses the shared tensor-unit matmul from upstream (core/affine_mm) and a new attention kernel. On the M5, the tensor units serve prompt calls only. Decode and windows use the twin. The M1 to M4 path does not change. The benchmarked build is fd2f8e27. The #873 head 76c3f4f8 adds only a fix for GPUs without tensor units.

Against mlx-lm: +5.8% at 2k, +7.0% at 8k, equal at 32k, −5.7% at 64k, −10.0% at 131k. Before, TensorFold was 2.7 to 3.2 times slower at every size. Served cold prefill shows the same: 4,428 → 13,031 tok/s at 8k, 2,243 → 6,199 at 131k.

01 · projections

Matmuls on the tensor units

The dense, conv and attention projections, and the experts, use core/affine_mm.

02 · attention

4 query heads, one K/V read

32 query heads share 8 KV heads. The new kernel stages each K/V block once for its 4 query heads and skips masked keys.

03 · chunks and loads

Fewer re-reads

Each prompt chunk re-reads the weights and the KV so far. Larger chunks and 8-byte fragment loads reduce this cost.

What does not change

Decode and windows stay on the twin. In process, decode after a prompt is the same as or higher than the PR head's (262 against 256 tok/s after 2k, 117.5 against 115.7 after 131k). Served, 4 streams on code: 490 → 557 tok/s (cheap windows). One stream on code: 291 → 279 tok/s. On the M5, the code reply has different tokens from the PR head's reply, so its drafts differ (216 rounds against 204, the same time per round). With tensor units off, the same build gives the PR head's tokens and 299.5 tok/s. Chat: 261.0 → 263.5. The M1 to M4 path keeps its kernels and its bits.

Exactness on the M5: the tensor units sum in a different order from the tiles. So a prompt row does not have the same bits as the same row in one-row decode. Every prompt call goes to the tensor units, so a prompt keeps its bits wherever the server cuts it. A resumed prompt equals a fresh one (a two-turn chat, cache on and off). Windows equal one-row decode, and concurrent replies equal solo runs (tf-lfm2-exact 4-bit 68 of 68 on the M5, 12 of 12 served). tf-lfm2-fp64: in every projection class and for attention, the worst error of the tensor path equals that of the tiles. The exactness and fp64 checks come from the earlier M5 tensor-unit run. The tensor kernels have not changed since.

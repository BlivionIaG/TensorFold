Inference, measured

The results.

This section compares TensorFold with mlx-lm 0.32.0 (mlx 0.32.3) on two machines. The Apple M4 Pro has a 20-core GPU and 48 GB. The Apple M5 Ultra has a 64-core GPU and 256 GB. Each machine runs 1 model process at a time. Both Macs ran the final build, fd2f8e27. It has cheap windows (#867, #868) and the exact 4-bit decode. The M5 Ultra also uses its tensor units for prompts (#871, #873). The M4 Pro has no tensor units. In the same session, mlx-lm and TensorFold ran in alternation. The quantized weights stay as stored

Inside one tile.

Each projection on quantized weights uses tile_qmm (the tiles) or its twin. Both read the codes as the checkpoint stores them. They expand the codes only in threadgroup memory or in registers. No bf16 copy of a weight matrix exists in device memory. On the M5 with tensor units (#871, #873), prompt projections use core/affine_mm instead. It runs on the tensor units and reads the same stored codes. Decode and windows use the twin on every Mac.

Where the gains come from

Same model, different kernels.

Both engines read the same 4-bit weights. mlx-lm runs general array operations from Python. TensorFold runs kernels written for this model. In each diagram, the top row shows mlx-lm. The bottom row shows the TensorFold kernels that do the same work.

Dispatch

07

Several streams and draft windows

The lane core puts the streams in 1 step. The rows then share the weight reads. In the PR head, the 4-bit twin reads the dense weights once for up to 4 rows. Cheap windows do this at every bit width. They use MMA from 8 rows. They read each picked expert once from 16 rows. Draft windows use the same path. Each reply equals its solo run.

We did not measure each difference alone. The decode gain comes from these differences together. One mlx-lm operation is not always one GPU kernel. The diagrams do not show views such as split and reshape. Sources: mlx-lm 0.32.0 models/lfm2_moe.py and models/switch_layers.py; TensorFold families/lfm2/forward.zig.

Cheaper windows · #867 and #868

Cheaper windows.

A window is several rows in 1 step. The rows come from a draft check, or 1 row comes from each stream. Decode time is mostly weight reads. In the PR head (#821 to #823), each extra row costs about half of a 1-row step. #867 and #868 share the reads across the rows. 1-row decode does not change. Every row keeps its bits.

Each concurrent reply equals its solo run (30 of 30). tf-lfm2-exact at the head of #873, 76c3f4f8, gave 68 of 68 at 4, 6 and 8 bits on the M4 Pro (8 bits: 3 runs). It gave 68 of 68 on the M5. The 4-bit codes are decoded as exact integers through half pairs (1024 + code, minus 1024). There is no integer-to-float convert.

Exactness

Same bits on every path.

A row gives the same bits in a prompt chunk, in decode and in a draft window. So drafted replies equal plain ones, concurrent replies equal solo ones, and a resumed prompt equals a fresh one.

matmul

Group sums in k order

The tiles (prompt chunks) and the twin (decode rows and windows, 1 to 32) give the same bits for each output by design. At load, twinExact checks this bit for bit. If a GPU differs, every row uses the tiles.

attention

Fixed 4,096-key chunks

The prompt kernel and the decode kernel come from one template. Each 32-key block has the same arithmetic. The parts merge in a fixed order.

receipts

Checked, not assumed

tf-lfm2-exact at the head of #873, 76c3f4f8, gave 68 of 68 at 4, 6 and 8 bits on the M4 Pro (8 bits: 3 runs). It gave 68 of 68 on the M5. At fd2f8e27 it crashed at 6 and 8 bits on the M4 Pro. A pipeline field was unset on GPUs without tensor units. 76c3f4f8 fixes this. Replies at 4 streams equal solo: 30 of 30 on the M4 Pro, 12 of 12 on the M5 Ultra.

The test used random 4-, 6- and 8-bit matrices, compared with float64. The error of the tiles is 2.4 to 3.9 times less than the error of mx.quantized_matmul on the same data (worst output, mean and worst column). Source: tile_qmm/tile_qmm_reference.json, mlx 0.32.3. This receipt is older. We did not rerun it on the final build.

On the M5 with tensor units on, one guarantee changes. The tensor units add 16 terms in an order that scalar code does not reproduce. So the prompt bits differ from the PR head. The greedy replies also differ: the code reply takes 216 draft rounds, not 204. These guarantees still hold. Windows equal 1-row decode. Concurrent replies equal solo runs (12 of 12). In the server, a resumed prompt equals a fresh one (2-turn check on the M5 Ultra, build 74aff635, an earlier tip).

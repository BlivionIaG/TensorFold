## What this changes

The kernel contract (docs/kernel-contract.md) runs on HIP. CONTRIBUTING asks every new or changed GPU kernel to register with it and to post each backend's `SUMMARY` line. Until now the contract's runners were Metal and CUDA only. The stack's HIP kernels register in the pull requests that add them.

- `tf-hip-kernel-contract` (`zig build hip-kernel-contract -Dhip-arch=ARCH`) runs gates 1 to 4 on the GPU for every registered HIP kernel, on the shared core harness (`zig/src/core/contract`). HIP is a backend beside Metal and CUDA. The core gates do not change.
- Each gate has a planted HIP control (`zig/kernels/hip/contract_controls.hip`, built with the kernels): a row max by `fmaxf`, a row sum by `atomicAdd`, a row sum that writes its input, a row sum that loses its tail input, and a dot summed in `__half`. Each must go red at its gate.
- Gate 5 checks every registered HIP launch against gfx1030, gfx1100, gfx1151 and gfx1201, one chip a generation (the caps table's). The records are in `zig/src/core/contract/hip_records.zig`: VGPRs, SGPRs, static LDS, scratch, the `__launch_bounds__` bound and the wave size, for each chip. The checks: threads within the bound and 1,024; wave32; VGPRs a wave within 256; VGPRs a SIMD within its file (1,024 on RDNA2, 1,536 on the others), a workgroup's waves spread over the WGP's four SIMDs; static plus dynamic LDS within 64 KiB.
- `zig build hip-kernel-contract-limits` compiles every kernel group and the controls for the four chips and reads each code object's AMDGPU metadata note (`zig/src/core/contract/hsaco.zig`, msgpack in the offload bundle's ELF). It prints `RECORD` lines and fails on a stale record. No GPU needed. `hip-kernel-contract-objects` installs the code objects.
- On the GPU, gate 5 also checks the device's limits against its chip's row, and each loaded kernel's VGPRs, LDS and thread limit against its record.
- Gate 5's HIP controls: a kernel launched at 512 threads past its `__launch_bounds__(256)`, and 40 KiB of static LDS launched with 32 KiB more. hipcc fits VGPRs to a kernel's bound, so a register overflow shows as a launch past its bound.
- The first registration: the RMS norm rows, a wave a row (`tf_rms_rows`, fp32, fp16 and bf16 out) and a block a row (`rms_kernel`, fp16 and bf16).
- `test-kernel-contract` and `zig build test` run the HIP records against the four chips, the metadata parser and the controls, with no GPU. The runner compiles against stub kernels in `zig build test`.

Shared code: the contract core gains HIP's chip table, launch and usage types and their check (`limits.zig`), and the records and the metadata reader. `zig/build/hip.zig` exposes its group compile for the four chips; the code objects it builds do not change. No production kernel changes.
